# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for
a skill generated by `create-verification-skill` (or any project verification
skill with a feature map). The unit of rigor is the feature, not every sentence:
cover every feature file from source and exercise every feature live, without
terminalising every bullet. Shape still matters when the facts are right: the
one-page bar is `../../references/skill-writing.md`.

## Outcomes

Pick one, and say which:

- **clean** — every feature got source and live coverage; nothing worth shipping.
- **changed** — one PR ships proven doc/harness/map corrections.
- **blocked** — coverage could not finish or a proven fix could not ship safely;
  say exactly what blocked it.

## Edit scope

Only edit the verify skill's own directory (its SKILL.md, features/, harness
scripts it owns). Never edit product code during a run: a behavior the map
describes that the app no longer does is either doc drift (fix the map) or a
product regression (report it, don't paper over it).

## Pass

0. **Locate the target.** The project-local skill whose body has
   launch/drive sections and a feature map (`.pi/skills/verify-<app>/`).
   Several candidates → ask which one; none → stop and point at
   `create-verification-skill` instead of inventing a target.

1. **Index and shape hygiene.** Read the feature map README and glob sibling
   files; fix missing/extra/duplicate/dead entries. Then the shape pass against
   `../../references/skill-writing.md`: the SKILL.md still routes (feature
   detail has not leaked into the body), the shared launch/drive recipe appears
   once, no dead section survives, and the description still names the app and
   its surfaces. A feature file past one screen splits by sub-feature.

2. **Source wave.** One readonly `agent` subagent per feature file, all
dispatched concurrently in one message
   (readonly: true). Each answers "how does this user-facing feature work?" from
   source, flags likely doc drift with citations, and returns one concise
   live-verification recipe (feature summary / source entry points / likely
   drift or none / one recipe). Children never drive the app and never edit files.

3. **Reconcile.** Merge overlapping recipes into as few app states as practical;
   spot-check cited drift, don't re-prove clean claims. Sweep recent churn for
   user-facing surfaces missing from the map — require a concrete source path
   before calling one missing.

4. **Live pass.** Required even when source looks clean. Follow the target
   skill's own Launch model; exercise every feature at least once, holding
   three invariants whatever the failure: (1) never drive an instance you
   haven't health-checked since it last did something surprising — doctor
   before first drive, after any failed drive, and reset-to-known or relaunch
   when doctor can't see the failure; (2) evidence captured so far survives
   every cleanup, checked at its named location, not assumed; (3) nothing a
   drive started outlives that drive's usefulness. A doctor failure caused by
   skill drift is drift: fix it under edit scope and retry once. A feature
   that can't be reached is `verified-unreachable` only with the concrete
   prerequisite (auth, entitlement, OS, external state) and the route
   attempted. Harness fixes from triage get re-driven live before shipping.

5. **Triage.** Wrong/missing user-POV description → doc drift, fix. Working
   behavior the harness can't drive → harness gap, fix (scripts executable,
   invocation documented in the body). Actually broken app behavior → product
   gap: record for the user, keep out of this PR.

6. **Ship or stop.** For changed: one PR of proven corrections, re-read every
   changed file first. For clean/blocked: no PR; report outcome and coverage
   honestly. Do not commit run notes.
